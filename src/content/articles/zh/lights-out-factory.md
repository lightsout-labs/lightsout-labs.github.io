我们的电子表格应用 [Gridworks](https://lightsout-labs.github.io/gridworks/) 已经上线了。它的仓库里有 58 个合并过的 PR，没有一个是人看过的。代码和测试都是 Agent 写的，PR 也是它开的，CI 一通过就自动合并，合并完自动部署。任何人现在打开它的网址，就能新建表格、导入自己的 `.xlsx` 文件来用。

这一周我们做的事情很少：回答 Agent 在整理需求时提的问题，在需求和设计两道关上输入 `approve`，后来又批准了 5 次需求变更，用过应用之后提了 5 个 issue。代码一次都没有打开过。

![GitHub 上 Gridworks 的 PR 列表，筛选条件是已合并：共 58 个，没有未关闭的。最新一个是 #63“feat: the workbook dialog (S40)”，11 月 20 日合并。](fig:gridworks-merged-pulls "Gridworks 在 GitHub 上已合并的 58 个 PR，最后一个合并于 11 月 20 日")

我们由此得出的看法很直接：只要需求写清楚，验证的办法也写下来，Agent 就能在没人看着的情况下把软件做出来。人写不写代码已经不重要了，重要的是规格说明，以及约束 Agent 产出的那些检查。

这篇写给还没亲眼见过现在的 Agent 能做到什么程度的工程师。下面讲我们做出了什么，靠什么代替读代码，一个缺陷是怎么在没人读代码的情况下修好的，以及这对写代码的人意味着什么。

## 做出来的是什么

Gridworks 是一个在浏览器里运行的电子表格，目标是覆盖 Excel 的主要功能，不用安装，不用注册。它能打开和保存真正的 `.xlsx` 文件，也能读写 `.csv`；能排序、筛选、冻结窗格、设置条件格式和数据验证、打印，断网也能用；界面有中文和英文，有浅色和深色两套主题。

下面的数字都是我们写这篇时对着 [gridworks 仓库](https://github.com/lightsout-labs/gridworks) 数出来的。

仓库的第一次提交在 11 月 13 日晚上 8 点 44 分，最后一个 PR 在 11 月 20 日下午 3 点 51 分合并，前后不到七天。`src` 下的产品代码有 75 个文件，共 25,651 行。公式引擎里实现了 184 个 Excel 函数。单元测试写了 470 多个，端到端测试写了 130 多个，后者在 Chromium、Firefox 和 WebKit 三个浏览器里各跑一遍。读写 `.xlsx` 用的不是现成的库：Agent 先用 ExcelJS，测出它光是载入一个 11 MB 的文件就要 4.5 秒，达不到需求里“10 MB 文件 5 秒内打开”的要求，于是记下一条[架构决策](https://github.com/lightsout-labs/gridworks/blob/main/docs/adr/0006-own-xlsx-reader.md)，自己写了读取器，后来又自己写了写入器。

整个过程拆成了 40 个切片，每个切片都有自己的 PR。其余的 PR 是需求、设计、需求变更、修缺陷前的规划，以及几次测试和 CI 的调整。

我们这一周的日常很单调。在终端里输入 `/nightshift:build`，Agent 找到待办清单里第一个没做完的切片，从最新的 `main` 拉一个分支，写测试，写代码，跑检查，交给评审，开 PR，等 CI 通过后合并。做完一个切片它就停下来，我们输入 `/clear` 清空上下文，再输入一次 `/nightshift:build`。大部分时候我们在做别的事，回来看一眼合并了什么，打开线上的 Gridworks 试一试新功能。

做的过程中需求改了 5 次。两次是我们自己想加的：11 月 16 日，我们想要 Excel 的 Point 模式（输入公式时用键盘和鼠标拾取引用），还有填充柄拖完之后的选项菜单。另外三次来自 issue，比如把启动时的整屏列表改成对话框。每一次都是先改需求文档，像最初那样等我们批准，再在待办清单里插入新的切片，照常开发。把启动屏换成对话框那一次，只改了一条需求，架构文档一字未动，实现它的切片改了 15 个文件。

## 什么代替了读代码

没人读代码，并不等于没人管质量。读代码这件事被拆成了几样东西，每一样都写在仓库里，每一次都会执行。

第一样是需求。`nightshift` 是我们写的一个 Claude Code 插件，Gridworks 就是用它做的。它的 `spec` 阶段会一直追问，直到需求写到可以检验的程度，然后停下来等我们批准。批准之后，需求文档就是 Agent 唯一的依据：设计从它来，待办清单里每个切片的验收标准从它来，测试又从验收标准来。每个切片都从清空的上下文开始，Agent 不记得上一个切片做过什么，只能读需求、架构、相关模块的设计说明和待办清单来接上进度。所以这些文档写下的东西必须完整，没写下的东西，下一个切片就不知道。

第二样是先写的测试。每个切片动手写代码之前，先把验收标准写成测试，跑一遍，确认它们因为功能还不存在而失败。规则不允许为了让检查通过而削弱测试、降低覆盖率下限或者放松 lint 规则。

第三样是另一个 Agent 的评审。每个切片做完，会交给一个只读的评审 Agent，它看得到差异、切片和相关模块的设计，看不到写代码时的那段对话。它的结论写进 PR 的描述里。40 个切片里，有 21 个被它挡下过，一共 26 个阻塞问题，都在开 PR 之前修掉了。比如单元格超链接那个切片，评审发现 `javascript:` 开头的链接也会被存下来并打开，修完之后只允许 `http:`、`https:` 和 `mailto:`。又比如公式运算那个切片，评审发现 `0^-1` 返回的是 `#NUM!`，而 Excel 返回 `#DIV/0!`，修复时补上了对应的测试。

第四样是 hook。写在提示词里的规则，模型可以不听；hook 在模型之外运行，它不听也得听。需要批准的文档，Agent 自己改不成已批准，只有人亲手输入 `approve` 才行；Agent 不能往 `main` 提交；`make check` 不通过，它就不能结束一个切片；同一个问题连修三次还不过，它会被要求停下来问人。

第五样是 CI 和三道关。每个 PR 都要过格式、lint、类型检查、带覆盖率下限的单元测试，以及三个浏览器里的端到端测试，全部通过才会自动合并。人守的三道关是批准需求、批准设计、验收交付。这一周我们只在前两道关上出现过。

![从上到下的流程图：spec，我们批准需求；design，我们批准设计；然后是 build，一次一个切片反复进行，fix 把我们报的缺陷变成切片，也交给 build；最后是 release，我们验收交付。](fig:stages-and-gates "nightshift 的五个阶段，和由我们做决定的三道关")

这几样东西合在一起，回答的是读代码原本要回答的问题：代码做的是不是需求要的。区别在于，它们每个 PR 都会完整执行一遍，不会因为人累了、赶时间了就跳过。

## 一个缺陷，从 issue 到修复

11 月 18 日上午，我们在 Gridworks 里输入 `=DATE(2026,11,18)`，单元格显示的是 `46344`。`=TODAY()`、`=NOW()`、`=TIME(14,30,0)` 也一样，全是数字。46344 没有算错，它就是 Excel 内部存储这一天用的序列号，只是 Excel 会把它显示成 `11/18/2026`。

我们提了 [#40](https://github.com/lightsout-labs/gridworks/issues/40)，内容只有几行：每个公式应该显示什么，现在显示的是什么。

之后的事都是 Agent 做的，我们只在终端里先后运行了 `fix` 和 `build` 两个命令。`nightshift` 的 `fix` 读了这个 issue，判断它违反了已经批准的需求（函数结果要和 Excel 一致），于是开了一个只改待办清单的 PR，在最前面插入修复切片 S35，把 issue 里的每个例子写成验收标准。这个 PR 下午 5 点 23 分合并。S35 照常先写测试，看着测试失败，再改代码，交给评审，开 PR。评审提了两个次要问题，都没有阻塞。5 点 40 分，修复 PR 合并，issue 自动关闭，新版本自动部署。

我们事后回头看了这个缺陷是怎么来的。负责日期函数的切片 S10，验收标准写的是：日期和时间函数对 Excel 文档里的例子返回和 Excel 一样的结果，“使用 Excel 的序列号”。测试照这句话检查序列号，全部通过。每一项检查都没有错，错在验收标准没有说清楚用户看到的应该是日期。

这件事最能说明我们的看法。缺陷出在规格上，修也是修在规格上：把“显示成日期”写进验收标准，测试就跟着改，代码就跟着改。整个过程中，没有人需要读代码，也没有人读了代码。

## 这对工程师意味着什么

同一份需求交给 Agent 做两遍，得到的代码不会一样，模块的切法、变量的名字、测试的写法都会不同。很多人因此觉得 Agent 不可靠。我们的看法是：只要验证是完整的，每一份结果都满足需求，它们的不同只落在需求没有规定的地方。那些地方，本来就不该有人在意。

所以工程师的功夫要换个地方下。过去花在写代码、读别人代码上的时间，要花到两件事上：把需求写到可以检验，把检验写到可以自动执行。S10 的那句验收标准，就在我们批准过的待办清单里，我们也放过了它。能把这种句子写对、也能把它挑出来的人，接下来最值钱。

回头看，这一周我们写下的东西全是规格：回答 `spec` 的提问，批准需求和变更，提 issue。#40 的正文就是一张对照表，每一行是一个公式、它应该显示什么、现在显示什么，Agent 把它几乎原样变成了 S35 的验收标准。写一个好 issue 和写一组好测试，用的是同一种功夫。人交给 Agent 的东西，最后都是规格。

我们也清楚这次证明了什么、没证明什么。证据只来自一个产品，用 TypeScript 写，做了不到七天，变化都不算大，还没经历过多年维护。第三道关还没过，Gridworks 还没有交付报告。验证完整这个前提，这次就没做到：日期缺陷是我们用产品时发现的，修好之后 S35 的备注里还记着一处和 Excel 不同的地方，`=TODAY()+7` 不会自动带上日期格式。验证能做到多完整，取决于需求写得多清楚，而这一步现在还要靠人。

如果你不信，最好的办法是自己做一遍。Gridworks 批准过的[需求文档](https://github.com/lightsout-labs/gridworks/blob/main/docs/requirements.md)就在仓库里。用 [`nightshift`](https://github.com/lightsout-labs/nightshift)，或者用你自己的流程，从这份需求开始把整个 Gridworks 做一遍，然后和我们的结果比一比：功能是不是都在，测试是不是都过，缺陷出在哪里。我们很想知道结果。
