# Architecture

Status: Approved

How the Lightsout Labs blog is built. What it must do is in
[requirements.md](requirements.md). Reasons for the decisions that are costly
to reverse are in the ADRs under `docs/adr/`. This document holds what spans
modules; the decisions inside one module are in `docs/design/<module>.md`.

## Overview

The blog is a static site generated by Astro from Markdown and published to
GitHub Pages. It has three parts. The **content** is plain files: articles
in `src/content/articles/<lang>/<slug>.md`, figure sources in `figures/`,
social posts in `social/`, and the style guide in `docs/style-guide.md`.
The **tools** turn and check that content: the figure renderer draws every
diagram and share card in a headless Chromium and writes optimized images
to `public/figures/`, and the content linter checks every article and post
against the style guide and the length, pairing, and figure rules. The
**site** is the Astro project that renders pages, feeds, and metadata from
the content. When the owner edits an article and pushes, CI runs
`make check` (which includes the linter) and `make e2e` (which builds the
site, renders figures, and drives the pages in a browser and Lighthouse);
after the pull request merges, the deploy workflow builds the same way and
publishes `dist/` to Pages.

## Stack

| Concern | Choice | Why |
|---|---|---|
| Site generator | Astro, static output, no client framework | Markdown content collections, per-language routes, and zero JavaScript by default (R22–R33); see [ADR 0001](adr/0001-astro-static-site.md). |
| Language | TypeScript, strict mode | One language for site, tools, and tests. |
| Feeds | `@astrojs/rss` | One feed per language (R27). |
| Sitemap | `@astrojs/sitemap` with i18n alternates | `sitemap.xml` with `hreflang` (R31). |
| Diagrams and charts | Mermaid, rendered by our figure renderer in Playwright's Chromium to WebP and PNG | Flowcharts, sequences, and simple charts from text; per-language, light and dark (R11, R12, R14); see [ADR 0002](adr/0002-figures-rendered-to-images-at-build.md). |
| Share cards | An HTML template rendered by the same renderer to PNG | Same tool, same fonts as diagrams; no second rendering stack (R28). |
| Image encoding | `sharp` | WebP at two widths and PNG for social posts (R14, R15, R16). |
| Fonts on pages | System font stacks for Latin and CJK | Nothing to download, so Lighthouse stays at 95 or higher (R30, R32). |
| Fonts in rendered images | Noto Sans SC (SIL OFL) from `@fontsource/noto-sans-sc`, pinned in the lockfile | Images look the same on every machine, and CJK labels measure correctly; the package keeps the font out of git and splits it by Unicode range. |
| X post length | `twitter-text` | X's own weighted-length rules, with links as 23 (R16). |
| Markdown figures | A remark plugin of our own, on `@astrojs/markdown-remark` | Turns `![alt](fig:name "caption")` into a `<figure>` with light and dark sources (R13, R29). Astro 7's default Markdown processor runs no remark plugins, so the unified one is installed. |
| Unit tests | Vitest | Content linter, series model, metadata. |
| End-to-end tests | Playwright on Chromium against `astro preview` | Pages, links, metadata, no-JS rendering, phone width. |
| Lighthouse | `@lhci/cli` with assertions at 0.95, mobile preset | R32, enforced in `make e2e`. |
| Lint and format | ESLint, Prettier, `astro check` | Code only; content has its own linter. |
| Runtime | Node.js LTS pinned in `.nvmrc`, npm | The default. |
| Hosting | GitHub Pages, deployed by GitHub Actions | Constraint (R22). |

## Modules

Each module has a small interface and hides substantial behavior. Tests go
through the interface only. Every module, layer, and dependency is here
because a requirement needs it.

| Module | Interface | Hides |
|---|---|---|
| `src/lib/series` | `seriesOf(entries)`, over the content collection's entries, giving `articles(lang)` (in series order, with part, slug, title, description, date, reading time), `article(lang, slug)`, `neighbours(lang, slug)` (previous, next, position "3 of 8"), `counterpart(lang, slug)`, `pageMeta(page)` (title, description, canonical, `hreflang` alternates, Open Graph and X card tags, JSON-LD `BlogPosting`) | Pairing articles across languages by slug; ordering by `part`; reading time (English words at 230 a minute, Chinese characters at 400 a minute); building absolute URLs and structured data (R19–R21, R24–R26, R28, R31). |
| `tools/content-lint` | `lint(repo)` giving a list of problems, each with file, line, and message; `articleLength(markdown, lang)`; a CLI that prints the problems and exits 1 if there are any | Parsing the style guide's rule blocks; stripping Markdown and code before counting; banned words, phrases, and patterns per language; em-dash, bold, and bullet density per 1,000 words; article and WeChat lengths; X weighted lengths and post counts; counterpart presence; figure references, alt text, captions, screenshot records; social images that the article uses (R3, R10–R21). |
| `tools/figures` | `make figures`: renders every diagram, screenshot, and share card into `public/figures/`, with a manifest `figures.json` of each figure's size and files | Launching Chromium; loading Mermaid with the site's light and dark palettes and the bundled font; the share-card template; resizing and encoding with `sharp`; output naming (R11, R12, R14, R15, R16, R28). |
| `tools/remark-figure` | A remark plugin, registered in the Astro config with the path of the manifest | Resolving `fig:<name>` to a diagram in the article's language or a shared screenshot; emitting `<figure>`, `<picture>` with a dark-scheme source, `srcset` at two widths, `width`, `height`, `loading="lazy"`, alt text, and `<figcaption>` (R10–R14, R29). |
| `src/` pages and layouts | Routes: `/` (root), `/<lang>/`, `/<lang>/<slug>/`, `/<lang>/rss.xml`, `/sitemap-index.xml`, `/robots.txt` | Layout, typography, theme, language switch, series navigation; nothing that `src/lib/series` can compute (R22–R30, R33). |

Decisions that span modules, cheap to reverse, with their reasons:

- **An article is identified by its slug**, the file name, shared by its
  English and Chinese versions. Pairing, the language switch, `hreflang`,
  and the counterpart check all use it. `part` in the front matter (1 to 12)
  gives the series order.
- **Article front matter** is `title`, `description` (the one-line summary,
  also the meta description), `date`, and `part`. The byline is not stored;
  it is always "Lightsout Labs" (R9).
- **A figure is named once and resolved per language.** Articles reference
  `fig:<name>`. A diagram has one source per language,
  `figures/diagrams/<name>.<lang>.mmd`, so labels are written natively, not
  substituted. A screenshot is `figures/screenshots/<name>.png` with a
  record `<name>.yml` (`shows`, `source`, and `taken`, which says when and
  how) and is shared by both languages. Screenshots are taken by hand, at a
  device scale factor of 2.
- **Generated images are not committed.** `public/figures/` is ignored by
  git and rebuilt by `make figures`, which `make check`, `make dev`,
  `make e2e`, and deployment run first, since `astro check` and
  `astro build` both render the articles. The remark plugin reads the
  renderer's manifest, so a build without it fails and names the command. Social posts point at the PNGs there, so the owner
  runs `make figures` before posting.
- **The style guide is the only home of the style rules.** Its banned
  items and density limits sit in fenced blocks tagged `style-rules-en` and
  `style-rules-zh` inside `docs/style-guide.md`; the linter reads them from
  there, so changing the guide changes the check; see
  [ADR 0003](adr/0003-style-rules-in-the-guide.md).
- **Counting rules.** English length is words; Chinese length is every
  character that is not whitespace or punctuation, which is how WeChat's
  editor and most Chinese editors count. Both exclude front matter, code
  blocks, figure syntax, and link targets. The content linter owns them, through
  `articleLength`; the series model computes reading time with it, so a
  page's reading time and the length check never disagree.
- **Social post files.** `social/<slug>/wechat.md` has front matter
  `headline` and `summary` and a Markdown body; `social/<slug>/x.md` holds
  the posts separated by lines of `---`. Images are written as
  `![alt](fig:name)` like in articles, and the linter prints the PNG path
  each resolves to, so the owner knows which file to upload.
- **A ledger of centrepiece examples.** `docs/examples.md` lists, for each
  published article, the `nightshift` and `gridworks` examples it is built
  around, with the file, commit, or pull request each comes from. Every
  article slice reads it before writing and adds its own entries, so no
  example is the centrepiece of two articles (R5).
- **Root page language choice.** `/` is a full page with links to both
  languages that works without JavaScript; a small inline script sends the
  visitor to `/zh/` when the browser prefers Chinese and to `/en/`
  otherwise (R23, R33).

## Data

There is no runtime data. All content is Markdown, YAML, Mermaid, and PNG
in the repository; the build output is static files.

## Repository layout

```
src/content/articles/en/   English articles, <slug>.md
src/content/articles/zh/   Chinese articles, <slug>.md
src/lib/series/            Series model and page metadata
src/pages/                 Routes
src/layouts/, src/components/, src/styles/
figures/diagrams/          <name>.en.mmd, <name>.zh.mmd
figures/screenshots/       <name>.png and <name>.yml
social/<slug>/             wechat.md, x.md
tools/content-lint/        Content linter and its CLI
tools/figures/             Figure renderer
tools/remark-figure/       Markdown figure plugin
tests/unit/, tests/e2e/    Vitest and Playwright tests
public/                    robots.txt, favicon; figures/ is generated
docs/style-guide.md        Voice, banned items, density limits
docs/examples.md           Centrepiece examples used by each article
.github/                   CI, deploy, issue template
```

## Make targets

| Target | Contents |
|---|---|
| `make check` | `make figures`, Prettier check, ESLint, `astro check`, Vitest with a coverage floor of 85% on `src/lib` and `tools`, the content linter (`node tools/content-lint/cli.ts`, run by Node's own TypeScript support), `scripts/check-docs.py` |
| `make e2e` | `make figures`, `astro build`, Playwright against `astro preview`, then Lighthouse CI on the root, both indexes, and every article page |
| `make figures` | Render diagrams, screenshots, and share cards into `public/figures/` |
| `make dev` | `make figures`, then the Astro dev server |

CI runs `make check` and `make e2e` on every pull request as the required
checks `check` and `e2e`. The `e2e` job runs in the Playwright container
image, which has Chromium for the figure renderer, the tests, and
Lighthouse. The `check` job installs Playwright's Chromium, since the
renderer runs in `make check` and in its unit test.

## Testing

| Level | Covers | How |
|---|---|---|
| Unit | Content linter rules, counting, X weighting, style-guide parsing, figure checks; series ordering, pairing, neighbours, reading time, metadata and JSON-LD; figure rendering and name resolution | Vitest on small fixture repositories under `tests/fixtures/` |
| End to end | Root language choice, index and article pages in both languages, language switch to the counterpart, series navigation, figures with light and dark sources, RSS validity, sitemap, `hreflang`, canonical, JSON-LD, share-card tags and images, content without JavaScript, no horizontal scroll at 360 px, dark theme | Playwright on Chromium |
| Lighthouse | Performance, Accessibility, Best Practices, SEO at 95 or higher on mobile | `@lhci/cli` assertions |
| Content | Style, length, pairing, figures, social posts | The content linter in `make check` |

The parts of the requirements that no script can judge, such as native
writing (R4), factual claims about `nightshift` and `gridworks` (R5, R6),
stated limits (R7), and titles that the body supports (R8), are checked by
the slice reviewer against the sibling repositories, and then by the owner
through issues (R34).

## Deployment

The `deploy` workflow runs on every push to `main`: it installs
dependencies in the Playwright container, runs `make figures` and
`astro build`, and publishes `dist/` with `actions/deploy-pages` to
`https://lightsout-labs.github.io`. A deployment is verified by the
workflow's last step, which fetches `/`, `/en/`, and `/zh/` from the live
site and fails unless each returns 200.
